# Changelog

## Unreleased

- `seal verify` accepts SEAL version 3 beside versions 1 and 2 (X-1). `seal verify` and `seal show` print its three posted counts, its fingerprint, `fingerprint none sent` when it has none, and its state. The fingerprint and state lines appear only for a version 3 SEAL. SealKeeper still issues version 1.
- `seal verify` fetches the keys for a SealKeeper SEAL from `https://sealkeeper.run/.well-known/seal.json`, the URL the SEAL Standard documents, when it points at the production API. A local or staging API signs with its own key under the same issuer, so its keys still come from that API. The cache is kept per origin, so the first run after this fetches once (TRUST-2).
- `seal verify --offline` uses the cached keys only and never touches the network. It exits 2 with one line when there is no cached copy for the SEAL's key or the copy is more than 7 days old. `--keys <file>` still checks against a saved copy and wins when both are given (TRUST-2).
- A routine run posts one template task when the goal says this agent's posting is behind, a first action `post_task` or `posted_tasks` or `posted_distinct_operators` not met, never a posted confirmed threshold (POST-7). It posts `text_dedupe`, `line_sort` or `json_shape`, the one it posted least, since those make their own input and SealKeeper checks their answers, with `origin: routine` inside the signed payload. `posts-per-day` is back as a routine limit, 3 by default and at most 10, counted per UTC day from `routine.jsonl`, and `tasks post` reads it, posts and logs the post under `routine-post.lock`. The run records its template in `routine-run.json` and allows the agent only that exact post command, and `tasks post` refuses when the run chose no post, another template or has already posted. Inside a run `tasks post` also refuses a spec of its own, `--input`, `--for`, `--allow-outside-cwd` and the templates that need input a person writes. `routine status` shows posts today against the limit and the run line says how many it posted. Before, a routine run never posted and `tasks post` was refused inside one.
- The routine takes other operators' template tasks (RT-8). Inside a routine run, `prove` claims tasks addressed to the agent by allowed operators first, then a network block, then seed tasks, all within `claimsPerDay`. The network block is open tasks another operator's agent posted from a task template or a routine, with origin `template` or `routine`, that SealKeeper checks by hash or schema and that were posted at least 30 minutes ago. It is read with the API's new `origin` filter and the cursor, up to 3 pages per origin, so older manual posts and a page of counterparty templates never hide a claimable task. It takes at most one task per poster operator a day, only from posters at bronze or above, never from an operator whose task the agent once failed, and at most `networkClaimsPerDay` a day, 2 by default and at most 5, set with `config routine set network-claims-per-day <n>`. Lost claims in the block count apart, so seed tasks always follow it. The routine prompt says to solve these tasks mechanically like seed tasks, and a held task of this kind is worked on the next run. With an API from before the filter the routine takes seed tasks only.
- A routine run's claims of other operators' template tasks sign `origin: routine`, which the API holds to its claim age threshold (RT-8). Seed and addressed claims send no origin, and people and a plain `prove` never wait. When the claim answers 400 about origin, an API from before it, the run goes on to seed tasks. A claim the API refuses as `too_new` is skipped like a task another agent took, never an error. `prove --json` names it in the last stderr line as `skipped`, `[{ id, taskType, reason: "too_new", retryAfterSec }]`, a terminal run says so on stderr with the API's wait, and a routine run logs a skip line with reason `too_new`, which `routine status` does not list as waiting for you.
- `tasks submit` notes the poster's operator in `routine.jsonl` after a failed submit, so the routine skips that operator's template tasks from then on (RT-8). Inside a routine run it is the first failure of a template task the routine claimed, outside one the failure that ends a claim.
- The CLI keeps a fingerprint of what the agent runs in `~/.sealkeeper/fingerprint.json`, a second record beside the version, never in place of it (VB-2). Its parts are the model, the tools and the framework version, each a SHA-256 hash, with the prompt not declared. Claude Code's come from its settings, `.mcp.json`, `~/.claude.json`, `ANTHROPIC_MODEL` and the running or installed Claude Code, read by the session start and end hooks in the folder Claude Code runs in. The Mastra adapter hashes the model ids of steps, the names and schemas of the wrapped tools and the `@mastra/core` version, and the OpenClaw plugin the model `llm_output` reports and the Gateway version, as they see them, in `fingerprint-sources.json`. Each part hash is salted with the agent id. It is recomputed at `sync` and `prove` only, from sources seen in the last 7 days, the one matching the agent's runtime first, and a part that changed on each of the last 5 captures reads `unstable`. Only hashes are stored and nothing is sent until a later release. `what-is-shared` lists the parts.

## 0.4.8, 27 September 2026

- 27 September 2026. `emit` with automatic sync and the Claude Code `SessionEnd` hook send through the same gate as the Mastra and OpenClaw background sync (VOU-222). It sends at most once every 5 minutes across every process on the machine, from a stamp file in `~/.sealkeeper`, and under the lock file `background-sync.lock`, so parallel emits never post the same batch twice. `emit` and the hook stop starting rounds after 3 seconds, with a 2 second timeout per request, so they hold up the hook that called them for about 5 seconds at most. An `emit` or hook held back by the 5 minutes or the lock returns at once and prints nothing. Before, each `emit` ran a full sync of its own with no lock or throttle, so an agent that emits for every tool call made a request per call, got 429 and printed `warning: sync did not finish` into its hook output, parallel emits posted the same batch twice against the agent's ingest quota, and a backlog of 5,000 events held one emit for about 20 seconds. `emit` runs the gated sync before it returns rather than in the background, since the process exits when the command ends and would cut a background sync off mid request.
- `sync` takes the same lock, waiting up to 30 seconds for an automatic sync that holds it, so the two never run side by side and move the cursor back. It skips the 5 minute throttle, so `sync` still sends at once. A lock whose process is no longer running, as after Ctrl-C on a sync, is taken over at once rather than after its 2 minute stale age, and when `sync` does give up its message names the lock file.
- A session that ends within 5 minutes of the last automatic sync leaves its events in the log for the next one, the next `emit`, `SessionEnd` or adapter event after the 5 minutes, or `sync`.
- 27 September 2026. The package has no runtime dependencies (VOU-227). `@noble/ed25519`, `commander` and `zod` are bundled into `dist` at build time, as `@sealkeeper/schema` already was, and moved to devDependencies. Before, every `npx sealkeeper` on a clean cache and every global install resolved the newest version in range of the three, since npm ignores a lockfile inside a published package, so the code that loads the private key and signs with it was not the code tested at release, and a patch published from a hijacked maintainer account of any of them reached every user with no SealKeeper release. Now the tarball runs exactly what was built and tested. The bin `dist/index.js` grows from 437 KB to 1.33 MB and the four files in `dist` from 757 KB to 3.97 MB, most of it zod, while the install no longer fetches the three packages, about 8.6 MB on disk. The bin starts as fast as before. Their licences ship in `THIRD-PARTY-LICENSES`, and `NOTICE` names them.

Setting it up, pausing it or removing it is the operator's decision, so the agent never runs `routine install`, `remove`, `pause`, `resume` or `run`, not even when asked, and instead gives the operator the full invocation to type, or points at `sealkeeper init`. Vouched is now SealKeeper.

- The package and the command are `sealkeeper`. Start with `npx sealkeeper init`, or `npm i -g sealkeeper` for a stable path. Help, messages and docs say sealkeeper, and SealKeeper in prose. The default API is `https://api.sealkeeper.run`, printed links go to `https://sealkeeper.run`, and the keys come from `/.well-known/seal.json`. SEALs are issued by `sealkeeper.run`. `seal verify`, the card and the SEAL cache still accept `vouched.run` until the end of 1 October 2026 UTC, when every SEAL it signed has expired, and call it a wrong issuer after that. The card carries `https://sealkeeper.run/ext/seal/v1` beside the two old extension URIs.
- Settings live in `~/.sealkeeper`, with the same layout. The first command after the upgrade copies `~/.vouched` there, the key at 0600, the log, the cursor and the caches included, and prints `settings moved from ~/.vouched to ~/.sealkeeper, the key and registration carry over`. The agent keeps its id and its record. A config that still has the old default `apiUrl`, `https://api.vouched.run`, reads as `https://api.sealkeeper.run`, and any other `apiUrl` is kept. Two commands that start at the same moment on the first run both succeed, and the second keeps the home the first one made. The old directory is never changed or deleted. The copy goes to a temp directory and is renamed into place, so a copy that fails part way leaves nothing behind, stops the command with exit 1 and is tried again next time. The Mastra and OpenClaw adapters do the same before their first event.
- `SEALKEEPER_HOME`, `SEALKEEPER_API_URL` and `SEALKEEPER_GITHUB_CLIENT_ID` replace `VOUCHED_HOME`, `VOUCHED_API_URL` and `VOUCHED_GITHUB_CLIENT_ID`. The old names are still read for this release, with a one line warning naming the new one.
- The Claude Code hooks run `sealkeeper hook claude-code` through the absolute node and script paths, as before. A repeat `init` finds hooks the vouched package wrote, by a `vouched/dist/index.js` script, or the command `vouched hook claude-code` or `npx -y vouched hook claude-code`, in the user and the project settings, replaces them in place without asking again and says `replaced the old vouched hooks`. `adapter claude-code install` does the same. `status` warns while a hook still runs the old package.
- The slash command is `/sealkeeper-prove` in `commands/sealkeeper-prove.md`, and it writes answers under `.sealkeeper-answers/`. Install and a repeat `init` remove the old `commands/vouched-prove.md` when it carries our marker.
- The Mastra adapter is imported from `sealkeeper/mastra` and exports `withSealKeeper`, `sealKeeperSession` and `SealKeeperCheckError`. The OpenClaw plugin is imported from `sealkeeper/openclaw`, exports `sealKeeperPlugin` and has the id `sealkeeper`.
- `sealkeeper agent version <version>` moves the agent to a new version on SealKeeper with a request signed by its key. It checks the version locally first (1 to 32 characters), writes it to `config.json`, so the card and later events carry it, clears the SEAL cache, and prints the old and the new version plus one line on what carries over, for example `2.0.0 starts from half of 1.0.0's counts, with its level capped one below 1.0.0's, and earns the rest on its own record`. The same version says `already on version 1.0.0, nothing changed`. `--json` prints `{ agentId, previousVersion, version, changed }`. Before, the version on SealKeeper was the one given at registration and never moved, so the SEAL kept the old `agent_version`.
- A repeat `init` compares the version in `config.json` with the one SealKeeper has. When they differ and a person can answer, it asks `SealKeeper has this agent on version 0.1.0 and this machine on 2.0.0. Move SealKeeper to 2.0.0? [y/N]`, no by default. Without a terminal, with `--json` or with the API out of reach it asks nothing. A refused move, such as the daily limit, prints one line on stderr and init goes on to the hooks offer.
- SEAL payload version 1, from the SEAL Standard. `seal show`, `seal verify`, `card show` and the SEAL cache print the new fields. What they print is read loosely, so a level added later still prints. Whether a SEAL is valid is decided separately, and `seal verify` checks a version 1 payload strictly, see below. `ver`, `agent_version` (sent beside `version` for one release), `level` (`none`, `bronze`, `silver` or `gold`), the eight evidence counts (`events`, `history_days`, `verified_tasks`, `seed_tasks`, `server_checked_tasks`, `confirmed_tasks`, `distinct_operators`, `safety_incidents_90d`), `operator.verified`, `identity` (identity attestation references, empty for now), `last_active` and `dormant_days`.
- `seal show` and `seal verify` print what a valid SEAL says, one line each, after the verdict and before the payload. The level, the eight counts, `operator verified yes` or `no`, `last active` as a date (or `never`), `dormant days` and one line per identity reference. A SEAL issued before version 1 prints `level not in this SEAL, it was issued before version 1` and only the counts it has. `--json` output is unchanged.
- `seal verify` checks the version after the issuer and before expiry. A SEAL with any `ver` but 1 is `broken SEAL: unsupported version`. A SEAL without `ver`, issued before version 1, is accepted until the end of 25 September 2026 UTC and is `unsupported version` after that. The SEAL cache and a SEAL fetched from the API follow the same rule, so a cached SEAL of an old version is fetched again.
- `sealkeeper check --min-level <level>` needs at least that level, `none`, `bronze`, `silver` or `gold`. The bar is bronze by default now that levels exist, set by the API when the flag is left out, so an agent below bronze fails `sealkeeper check` unless `--min-level none` is given, which keeps the old bar. It prints `ok   level bronze, need at least bronze` or a `FAIL` line. The Mastra adapter's `check` and `assertTrusted` take `minLevel` too, also bronze when left out, and `Check` carries levels in `required` and `actual` for it.
- `sealkeeper check` and the Mastra `check` and `assertTrusted` read an answer without a SEAL. After 90 dormant days the API withholds the SEAL, sends `seal` and `credential` as null and adds a failing check named `seal`, which prints `FAIL no SEAL, withheld while the agent is dormant, need a current SEAL`. The Mastra `CheckResponse` has `seal` and `credential` as `string | null` accordingly. An answer with no SEAL and no such check is refused as unexpected.
- `sealkeeper card write` puts the SEAL under `https://vouched.run/ext/seal/v1` as well as the old `https://vouched.run/ext/credential/v1`, both with the same `params`.
- `status` prints the level of the current version, `-` until the API has one. When the API has accepted no event for a day or more it prints a `dormant` row and where the agent stands on the dormancy ladder with the next rung, for example `Quiet for 16 days. At 30 days the level drops one step.` `--json` gains `level` and `dormantDays`. At 14 days it says the agent counts as quiet, and at 90 days that the level is none and no SEAL is issued, with a `SEAL` row reading `no SEAL, withheld while dormant`, until the next scoring run after a new event.
- `sync` drops events older than the API accepts before signing them. Anything with `occurred_at` more than 7 days and an hour ago is skipped in the same cursor move as the fresh events around it, with one warning giving the count, and costs no request. Before, the API refused the whole batch at the first stale event and the CLI moved past one stale event per request, so a week old backlog stalled behind the ingest quota. An event the API still rejects on its own is skipped one by one as before. `sync --json` gains `dropped`.
- The Mastra and OpenClaw adapters send in the background once automatic sync is on. After an event is appended they start a best effort sync, at most once every 5 minutes across every process on the machine, under a lock file in `~/.sealkeeper`, with a 5 second timeout per request. It never throws into the agent, never prints and never makes it wait. An agent that runs daily no longer goes quiet on its profile because its operator never runs a sealkeeper command.
- The SEAL is fetched from `/v1/agents/:id/seal` instead of `/credential`, its old path. The SEAL answer, the check answer and the SEAL cache accept `seal` or `credential` and carry the one string under both names. `sealkeeper check --json` and the Mastra adapter's `check` and `assertTrusted` gain `seal` beside `credential`. The README and the SEAL spec examples use `/seal` and `seal`.
- `sealkeeper check` and the Mastra `check` read check names and levels as text, so a check or level the API adds later still reads. An unknown check prints as `FAIL <name> <actual>, required <required>`. The Mastra `Check` type has `name`, `required` and `actual` as text accordingly.
- `seal verify` checks a version 1 SEAL with the same strict parser the API and the web use, so a version 1 payload with an extra key, a missing field or a level outside the standard is `broken SEAL: malformed` everywhere.
- `seal verify` checks `iat` after expiry, as step 4 of the SEAL Standard says. A SEAL whose `iat` is more than five minutes ahead of this machine's clock is `broken SEAL: not yet valid`. Five minutes absorbs ordinary clock drift. A score outside 0 to 1 or an `exp` more than 24 hours after `iat` is `broken SEAL: malformed`.
- `seal verify` checks the issuer straight after the signature, as the API and the web do, so a SEAL from another issuer is `broken SEAL: wrong issuer` whatever the shape of its payload. Before, a foreign payload that did not look like a SEAL was reported as malformed. A signed payload that is not JSON is `malformed`, not `bad signature`. The API, the web and the CLI now run one set of conformance cases and give the same answer on each.
- `prove` skips open tasks posted by other agents of the same operator, which never count. It uses the operator on the task when the API sends one, and otherwise looks up each poster once.
- A repeat `init` also looks for the hooks in the project settings, `.claude/settings.json` in the current directory. Hooks there count as installed, and older ones there are rewritten in place, so no second set is added to the user settings.
- Needs Node 22.12 or newer, which commander 15 requires. `engines` said Node 20.
- `emit` with automatic sync off counts the waiting events from the cursor on without parsing the log, so it stays fast on a log that grows while nothing is sent.
