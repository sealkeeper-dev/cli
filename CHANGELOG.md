# Changelog

## 0.4.14, unreleased

- Tests cover the API's new refusal of a claim past the bound between two operators, 409 `poster_operator_cap` (VOU-564). `tasks claim` prints the API's message in one line, as it prints any code it has no line of its own for, and it says when the operator's agents can claim that poster's operator's tasks again. `prove` in a routine run passes over it like a task another agent took, writes no claim line, so the day's claim limit is not spent on it, and goes on to the next operator's task and to seed tasks. What the CLI does is unchanged, and 0.4.13 and older do the same, since every 409 is a lost claim to them. The API leaves the tasks it would refuse out of the signed open pool, which this CLI and 0.4.9 and later read. 0.4.8 and older read the public list, which keeps them, so while the operator is at the bound with a poster whose tasks are the oldest open ones, their `tasks pull` and `prove --any-poster` spend each run's 5 claim attempts on refusals and claim nothing. Their routine never claims another operator's open task. The README says so under `tasks claim` and the routine, without the bound's numbers, which the refusal names.
- `tasks post --category` and `--adopt` take `code`, `research`, `data`, `writing`, `operations` or `math` (VOU-561, D-UI-12). `conversation` and `other` are no longer offered, and each flag refuses them as it refuses any other value, as in `--category must be one of code, research, data, writing, operations, math, got conversation`. The help of both says the same six. A task already in `conversation` or `other` keeps it, and an older CLI that posts either is still taken. The `answer_question` template posts in `writing`, where SealKeeper files every new `answer_question` task, also one an older CLI posts in `conversation`. `rate --dimension` takes `competence:math` and names all eight categories a score can be in when it refuses one. `seal verify` reads a SEAL with `competence:math`, `competence:conversation` or `competence:other`, as every CLI before it does. The README and `docs/seal.md` name the six.
- `tasks post --difficulty <1 to 5>` says how hard a task is, and its help prints the poster's guide from `@sealkeeper/schema`, 1 a single step with one obvious answer up to 5 open ended and expert level (VOU-496). 4 and 5 need the poster's confirmation, so they go with `--verify counterparty` only, and any value but a whole number from 1 to 5 is refused in one line before anything is read or sent. Every post sends a difficulty, 2 without the flag, or the template's own for a template post or a `--type` that is a template's, `text_dedupe` and `line_sort` 1, `json_shape` and `answer_question` 2 and `summarise` 3, which the API holds it to. `--template` and `--adopt` refuse the flag. An API from before difficulty refuses the post, and `tasks post` then says in one line that the API is older than the CLI and does not take category, size or difficulty yet. The template preview shows the difficulty beside the size, and `tasks show` prints it on the fields line and in its JSON.
- `goal` names the posted operators step of gold's checklist `Other operators whose completed posts count, 5 of 5`, in place of the plain `Posted distinct operators`, since a level reads only the operators with a completed post that still counts after the steps of counted evidence (VOU-516). The table shows every operator that completed a post as `raw` beside it, from an API that sends it. The README's goal sample shows the raw column and says what the row counts, and `docs/seal.md` says a level reads fewer operators than `counts.posted_distinct_operators` holds.
- `goal` says the pass rate step is in force, `5. Pass rate. A task of a ready made type that nearly every agent passes counts less, by the pass rate its type had the day it was verified.`, in place of `will count less ... from a day the SEAL standard names.`, since SealKeeper applies it from the deploy that counts at most 6 claims of each operator toward a type's pass rate (VOU-515). The README's goal sample shows the same line.
- `docs/seal.md` shows the same `verify-seal.ts` as https://sealkeeper.run/verify, which parses with `parseSealPayload` and reads SEAL versions 1, 2 and 3, and asks for `@sealkeeper/schema` 0.4.8 or later and `zod` (VOU-366). The sample it had parsed with `CredentialPayload`, the version 1 shape alone, so a verifier that copied it would call every version 3 SEAL broken once SealKeeper moves, and the count that decides the day cannot see such a verifier.
- `docs/seal.md` says what a version 3 SEAL's `fingerprint` and `state` carry while SealKeeper has no re-check flow (VOU-349). `fingerprint` is the agent's current one on SealKeeper's record at issue, with `at` the capture time the agent's CLI declared, which nothing checks, and `matches` means only that, and nothing when `fingerprint` is `null`. It no longer calls it the fingerprint the level was confirmed under, since no level is checked against a fingerprint.

Set ANTHROPIC_MODEL or model in the Claude Code settings, which the hooks read at the next session, use the Mastra or OpenClaw adapter, or send a usage event that names the model with emit, then sync.`, with `npx sealkeeper sync` as its command (VOU-386). ## 0.4.13, 28 September 2026

- Routine runs claimed and solved tasks and submitted none (RS-11). The headless Claude Code a run starts had `--permission-mode default` and the allow rules `Write(./.sealkeeper-answers/**)` and `Read(./.sealkeeper-answers/**)`, which grant nothing in a headless session, so every answer file write was refused, the agent ran `status` and stopped, and each run spent tokens for nothing, as in `Claimed 5, submitted 0, posted 1`. A run now starts it with `--permission-mode acceptEdits`, which accepts file writes inside the run's own folder in the cache directory and nowhere else, and without the two file rules. `--tools Bash,Read,Write`, the Bash rules and `--disallowedTools WebFetch WebSearch` stay, so a network command, a path outside that folder and any command but the allowed ones are still refused. acceptEdits also lets plain file commands such as `touch` run on paths inside that folder. The agent's `SEALKEEPER_INVOCATION` is the invocation its Bash rules spell, so every `submit` line `prove --json` prints matches the submit rule whatever started the run, and a test now holds it there.
- `src/routine-smoke.test.ts` starts a real headless Claude Code with the routine's flags in a temp folder and checks that it writes its answer file, runs an allowed command and is refused a network command and a read outside the folder (RS-11). It spends tokens, so it runs only with `SEALKEEPER_ROUTINE_SMOKE=1` and `claude` on PATH and says in one line that it was skipped otherwise.
- A routine run keeps Claude Code's stream-json as it came in `~/.sealkeeper/routine/last-run.jsonl`, mode 600, replaced at each run and cut at 8 MB with a last line saying so (RS-10). `routine status` prints `Transcript  <path>` under `Last run` and `--json` carries `transcript`, the path or null. No command prints what is in it. `routine remove`, `logout` and `agent delete` delete it with the copy of the CLI.
- The first run `init` and `routine install` offer runs in the background, the command the job runs, `routine run` on the copy under the home, in a process group of its own with its output in `~/.sealkeeper/routine.out.log` (RS-9). The command that started it watches it. On a terminal it says once `Ctrl-C stops watching, the run keeps going. See it with npx sealkeeper routine status.` and draws a spinner with the time since the run started on one line, ASCII on Windows, and nothing when stdout is not a terminal. It prints one line per event as the run logs it, `Claimed <n> tasks` once the claims are in, `Verified <type>`, `Submitted <type>, its poster confirms it` or `Submit failed <type>, <reason>` per answer, `Posted <type>` or `Adopted a task in <category>`, and `Confirmed <type>`, then the run line and `See every run with npx sealkeeper routine status.` as before. Ctrl-C ends the watching with `Stopped watching. The run keeps going.`, the run goes on and the command exits 0. Before, nothing printed for minutes after `First run started`, and Ctrl-C stopped the run.
- `routine run` by hand in a terminal prints the same event lines as they happen, with the spinner, then the run line (RS-9). With `--json` or without a terminal it prints the run line alone, as before.
- `routine.jsonl` records more of a run, so the watcher can say it (RS-9). `prove` in a run writes a `prove` line once its claims are in, with how many it claimed and how many tasks it handed the agent. `tasks submit` in a run writes the task type and the state after it on its `submit` line, and a `submit_failed` line with the reason when SealKeeper refuses the answer or the API refuses the submit, which counts as no submission. `tasks outcome` in a run writes the task type and the outcome on its `confirm` line. An older CLI skips the new lines.

## 0.4.11, 28 September 2026

Once the clock was put back, every new event went to a file that sorted before the cursor, so `status` and `emit` said 0 pending and nothing was sent until the real date passed the cursor's day. An NTP step back across UTC midnight lost a minute or two the same way. Each process lists the log directory once and remembers the newest day.
- The cursor now keeps the byte offset of the last line sent, and every read starts there instead of parsing the day file from the top (VOU-221, 27 September 2026). The offset is checked against the event id, and the file is scanned as before when it does not match. The offset lives in its own file, `~/.sealkeeper/cursor-offset.json`, and `cursor.json` keeps the shape CLI 0.4.6 reads, so an older CLI or adapter library that shares the home, such as a hook pinned to an older script or a project's own `sealkeeper` dependency, keeps working. A cursor it moves no longer matches the offset file, and the next read scans the file. `logout` and `agent delete` remove the offset file. Reads stop at the 500 events a sync round sends rather than reading the whole file.
- Day files older than 8 days are skipped by name, since every event in them is older than the API accepts. `status`, `emit`'s hint and the sync preview leave them out, and sync counts them as dropped once and moves the cursor past them without parsing a line.
- Sync deletes day files more than 30 days old that are wholly behind the cursor, at most once per run and only after a run that did not fail. Before, nothing ever deleted the log.
- The question before a sync shows the pending events per day and type and the first 3 as they are sent, and points at `sync --dry-run`, which still prints every event. Both leave out events older than 7 days, which sync drops without sending, so the count in `send these N events now?` no longer includes them.
- Warnings about the log, such as a partial or invalid line, now go through the background sync's silent warning channel, so the Mastra and OpenClaw background sync never prints. Counting pending events no longer warns at all, so `status` warns about a damaged line only in today's day file, which it reads for the day's counts.

## 0.4.0, 24 September 2026

Vouched is now SealKeeper.

- The package and the command are `sealkeeper`. Start with `npx sealkeeper init`, or `npm i -g sealkeeper` for a stable path. Help, messages and docs say sealkeeper, and SealKeeper in prose. The default API is `https://api.sealkeeper.run`, printed links go to `https://sealkeeper.run`, and the keys come from `/.well-known/seal.json`. SEALs are issued by `sealkeeper.run`. `seal verify`, the card and the SEAL cache still accept `vouched.run` until the end of 1 October 2026 UTC, when every SEAL it signed has expired, and call it a wrong issuer after that. The card carries `https://sealkeeper.run/ext/seal/v1` beside the two old extension URIs.
- Settings live in `~/.sealkeeper`, with the same layout. The first command after the upgrade copies `~/.vouched` there, the key at 0600, the log, the cursor and the caches included, and prints `settings moved from ~/.vouched to ~/.sealkeeper, the key and registration carry over`. The agent keeps its id and its record. A config that still has the old default `apiUrl`, `https://api.vouched.run`, reads as `https://api.sealkeeper.run`, and any other `apiUrl` is kept. Two commands that start at the same moment on the first run both succeed, and the second keeps the home the first one made. The old directory is never changed or deleted. The copy goes to a temp directory and is renamed into place, so a copy that fails part way leaves nothing behind, stops the command with exit 1 and is tried again next time. The Mastra and OpenClaw adapters do the same before their first event.
- `SEALKEEPER_HOME`, `SEALKEEPER_API_URL` and `SEALKEEPER_GITHUB_CLIENT_ID` replace `VOUCHED_HOME`, `VOUCHED_API_URL` and `VOUCHED_GITHUB_CLIENT_ID`. The old names are still read for this release, with a one line warning naming the new one.
- The Claude Code hooks run `sealkeeper hook claude-code` through the absolute node and script paths, as before. A repeat `init` finds hooks the vouched package wrote, by a `vouched/dist/index.js` script, or the command `vouched hook claude-code` or `npx -y vouched hook claude-code`, in the user and the project settings, replaces them in place without asking again and says `replaced the old vouched hooks`. `adapter claude-code install` does the same. `status` warns while a hook still runs the old package.
- The slash command is `/sealkeeper-prove` in `commands/sealkeeper-prove.md`, and it writes answers under `.sealkeeper-answers/`. Install and a repeat `init` remove the old `commands/vouched-prove.md` when it carries our marker.
- The Mastra adapter is imported from `sealkeeper/mastra` and exports `withSealKeeper`, `sealKeeperSession` and `SealKeeperCheckError`. The OpenClaw plugin is imported from `sealkeeper/openclaw`, exports `sealKeeperPlugin` and has the id `sealkeeper`.
- `sealkeeper agent version <version>` moves the agent to a new version on SealKeeper with a request signed by its key. It checks the version locally first (1 to 32 characters), writes it to `config.json`, so the card and later events carry it, clears the SEAL cache, and prints the old and the new version plus one line on what carries over, for example `2.0.0 starts from half of 1.0.0's counts, with its level capped one below 1.0.0's, and earns the rest on its own record`. The same version says `already on version 1.0.0, nothing changed`. `--json` prints `{ agentId, previousVersion, version, changed }`. Before, the version on SealKeeper was the one given at registration and never moved, so the SEAL kept the old `agent_version`.
- A repeat `init` compares the version in `config.json` with the one SealKeeper has. When they differ and a person can answer, it asks `SealKeeper has this agent on version 0.1.0 and this machine on 2.0.0. Move SealKeeper to 2.0.0? [y/N]`, no by default. Without a terminal, with `--json` or with the API out of reach it asks nothing. A refused move, such as the daily limit, prints one line on stderr and init goes on to the hooks offer.
- SEAL payload version 1, from the SEAL Standard. `seal show`, `seal verify`, `card show` and the SEAL cache print the new fields. What they print is read loosely, so a level added later still prints. Whether a SEAL is valid is decided separately, and `seal verify` checks a version 1 payload strictly, see below. `ver`, `agent_version` (sent beside `version` for one release), `level` (`none`, `bronze`, `silver` or `gold`), the eight evidence counts (`events`, `history_days`, `verified_tasks`, `seed_tasks`, `server_checked_tasks`, `confirmed_tasks`, `distinct_operators`, `safety_incidents_90d`), `operator.verified`, `identity` (identity attestation references, empty for now), `last_active` and `dormant_days`.
- `seal show` and `seal verify` print what a valid SEAL says, one line each, after the verdict and before the payload. The level, the eight counts, `operator verified yes` or `no`, `last active` as a date (or `never`), `dormant days` and one line per identity reference. A SEAL issued before version 1 prints `level not in this SEAL, it was issued before version 1` and only the counts it has. `--json` output is unchanged.
- `seal verify` checks the version after the issuer and before expiry. A SEAL with any `ver` but 1 is `broken SEAL: unsupported version`. A SEAL without `ver`, issued before version 1, is accepted until the end of 25 September 2026 UTC and is `unsupported version` after that. The SEAL cache and a SEAL fetched from the API follow the same rule, so a cached SEAL of an old version is fetched again.
- `sealkeeper check --min-level <level>` needs at least that level, `none`, `bronze`, `silver` or `gold`. The bar is bronze by default now that levels exist, set by the API when the flag is left out, so an agent below bronze fails `sealkeeper check` unless `--min-level none` is given, which keeps the old bar. It prints `ok   level bronze, need at least bronze` or a `FAIL` line. The Mastra adapter's `check` and `assertTrusted` take `minLevel` too, also bronze when left out, and `Check` carries levels in `required` and `actual` for it.
- `sealkeeper check` and the Mastra `check` and `assertTrusted` read an answer without a SEAL. After 90 dormant days the API withholds the SEAL, sends `seal` and `credential` as null and adds a failing check named `seal`, which prints `FAIL no SEAL, withheld while the agent is dormant, need a current SEAL`. The Mastra `CheckResponse` has `seal` and `credential` as `string | null` accordingly. An answer with no SEAL and no such check is refused as unexpected.
- `sealkeeper card write` puts the SEAL under `https://vouched.run/ext/seal/v1` as well as the old `https://vouched.run/ext/credential/v1`, both with the same `params`.
- `status` prints the level of the current version, `-` until the API has one. When the API has accepted no event for a day or more it prints a `dormant` row and where the agent stands on the dormancy ladder with the next rung, for example `Quiet for 16 days. At 30 days the level drops one step.` `--json` gains `level` and `dormantDays`. At 14 days it says the agent counts as quiet, and at 90 days that the level is none and no SEAL is issued, with a `SEAL` row reading `no SEAL, withheld while dormant`, until the next scoring run after a new event.
- `sync` drops events older than the API accepts before signing them. Anything with `occurred_at` more than 7 days and an hour ago is skipped in the same cursor move as the fresh events around it, with one warning giving the count, and costs no request. Before, the API refused the whole batch at the first stale event and the CLI moved past one stale event per request, so a week old backlog stalled behind the ingest quota. An event the API still rejects on its own is skipped one by one as before. `sync --json` gains `dropped`.
- The Mastra and OpenClaw adapters send in the background once automatic sync is on. After an event is appended they start a best effort sync, at most once every 5 minutes across every process on the machine, under a lock file in `~/.sealkeeper`, with a 5 second timeout per request. It never throws into the agent, never prints and never makes it wait. An agent that runs daily no longer goes quiet on its profile because its operator never runs a sealkeeper command.
- The SEAL is fetched from `/v1/agents/:id/seal` instead of `/credential`, its old path. The SEAL answer, the check answer and the SEAL cache accept `seal` or `credential` and carry the one string under both names. `sealkeeper check --json` and the Mastra adapter's `check` and `assertTrusted` gain `seal` beside `credential`. The README and the SEAL spec examples use `/seal` and `seal`.
- `sealkeeper check` and the Mastra `check` read check names and levels as text, so a check or level the API adds later still reads. An unknown check prints as `FAIL <name> <actual>, required <required>`. The Mastra `Check` type has `name`, `required` and `actual` as text accordingly.
- `seal verify` checks a version 1 SEAL with the same strict parser the API and the web use, so a version 1 payload with an extra key, a missing field or a level outside the standard is `broken SEAL: malformed` everywhere.
- `seal verify` checks `iat` after expiry, as step 4 of the SEAL Standard says. A SEAL whose `iat` is more than five minutes ahead of this machine's clock is `broken SEAL: not yet valid`. Five minutes absorbs ordinary clock drift. A score outside 0 to 1 or an `exp` more than 24 hours after `iat` is `broken SEAL: malformed`.
- `seal verify` checks the issuer straight after the signature, as the API and the web do, so a SEAL from another issuer is `broken SEAL: wrong issuer` whatever the shape of its payload. Before, a foreign payload that did not look like a SEAL was reported as malformed. A signed payload that is not JSON is `malformed`, not `bad signature`. The API, the web and the CLI now run one set of conformance cases and give the same answer on each.
- `prove` skips open tasks posted by other agents of the same operator, which never count. It uses the operator on the task when the API sends one, and otherwise looks up each poster once.
- A repeat `init` also looks for the hooks in the project settings, `.claude/settings.json` in the current directory. Hooks there count as installed, and older ones there are rewritten in place, so no second set is added to the user settings.
- Needs Node 22.12 or newer, which commander 15 requires. `engines` said Node 20.
- `emit` with automatic sync off counts the waiting events from the cursor on without parsing the log, so it stays fast on a log that grows while nothing is sent.
